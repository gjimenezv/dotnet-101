Entity Framework Core — cheat sheet

De la lección 6. Pensado para repasar en 5 minutos antes de la prueba.

DbContext + modelo

public class AppDbContext : DbContext
{
    public DbSet<Product> Products { get; set; }
    public DbSet<Order> Orders { get; set; }
}

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}

DbContext = Unit of Work. DbSet<T> = Repository (ya implementado por EF Core).

Migrations (CLI)

dotnet ef migrations add InitialCreate
dotnet ef database update

Queries con LINQ

var expensive = await _context.Products
    .Where(p => p.Price > 100)
    .OrderByDescending(p => p.Price)
    .ToListAsync();

var withCustomer = await _context.Orders
    .Include(o => o.Customer)          // como un LEFT JOIN
    .Where(o => o.Total > 1000)
    .ToListAsync();
Filtrá antes de .ToListAsync() — si no, traés toda la tabla a memoria primero.

CRUD

// Create
_context.Products.Add(new Product { Name = "Mouse", Price = 25.99m });
await _context.SaveChangesAsync();

// Update (tracking automático)
var p = await _context.Products.FindAsync(id);
p.Price = 19.99m;
await _context.SaveChangesAsync();

// Delete
_context.Products.Remove(p);
await _context.SaveChangesAsync();

Repository pattern (opcional sobre EF Core)

public interface IProductRepository
{
    Task<Product?> GetByIdAsync(int id);
    Task<List<Product>> GetAllAsync();
    Task AddAsync(Product product);
}
Agregar repository propioUsar DbContext directo
Mockeable en tests sin DB realMenos indirección, más simple
Aísla el dominio de EF CoreAcceso total a LINQ sin fricción
Útil en apps grandes/complejasSuficiente en apps chicas/medianas

Respuesta de entrevista si preguntan "¿usarías repository pattern?": "Depende — EF Core ya actúa como repository/unit of work internamente. Agregaría una capa propia si necesito aislar el dominio de EF o testear sin base de datos; si no, el DbContext directo es más simple y suficiente."
