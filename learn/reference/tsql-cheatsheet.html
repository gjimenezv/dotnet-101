Orden lógico de ejecución

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

WHERE filtra antes de agrupar; HAVING filtra después. WHERE no puede usar un alias definido en SELECT.

SELECT + JOIN

SELECT o.Id, o.Total, c.Name AS CustomerName
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.Id
WHERE o.Total > 100
ORDER BY o.Total DESC;
JOINDevuelve
INNER JOINSolo filas con match en ambas tablas
LEFT JOINTodas las filas de la izquierda + NULL si no hay match a la derecha

Regla: "todos los X, tengan o no Y" → LEFT JOIN desde X.

Agregaciones

SELECT CustomerId, COUNT(*) AS OrderCount, SUM(Total) AS TotalSpent
FROM Orders
GROUP BY CustomerId
HAVING SUM(Total) > 1000;
COUNT(*)cantidad de filas por grupo
SUM / AVG / MIN / MAXagregados numéricos
GROUP BYagrupa filas por columna(s)
HAVINGfiltra grupos ya agregados

Stored procedure

CREATE PROCEDURE GetOrdersByCustomer
    @CustomerId INT,
    @MinTotal DECIMAL(10,2) = 0     -- parámetro opcional
AS
BEGIN
    SELECT Id, Total, OrderDate
    FROM Orders
    WHERE CustomerId = @CustomerId
      AND Total >= @MinTotal
    ORDER BY OrderDate DESC;
END;

-- Ejecutar:
EXEC GetOrdersByCustomer @CustomerId = 42, @MinTotal = 100;

Optimización básica: índices y table scans

CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
ConceptoQué es
Clustered indexOrdena físicamente las filas de la tabla. Solo puede haber uno — SQL Server lo crea automático con tu PRIMARY KEY
Nonclustered indexEstructura aparte que apunta a las filas. Podés tener varios — creálo en columnas que uses seguido en WHERE/JOIN y que no sean ya la PK
Table scanSQL Server lee toda la tabla fila por fila porque no hay índice útil — lento en tablas grandes, la señal más común de "esta query necesita un índice"
EF Core ya indexa automático toda columna FK (ver lección 7) — un índice manual solo hace falta en columnas que filtrás/ordenás seguido y que no son ya una FK, como Orders.OrderDate o Customers.City.

El problema N+1 (EF Core, no T-SQL puro)

// N+1: 1 query para Orders + 1 query POR CADA Order para su Customer
foreach (var order in await _context.Orders.ToListAsync())
    Console.WriteLine(order.Customer.Name);   // dispara un SELECT por vuelta

// 1 sola query con JOIN
var orders = await _context.Orders.Include(o => o.Customer).ToListAsync();

Si te preguntan "¿cómo optimizarías esta query lenta?" y ves un loop con acceso a una navigation property adentro, la respuesta casi siempre es .Include() (o .Select() proyectando solo lo que necesitás).
