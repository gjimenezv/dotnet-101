T-SQL: queries, JOINs y stored procedures

Objetivo: leer y escribir SELECTs con JOINs y agregaciones, y crear un stored procedure simple con parámetros.

SQL es declarativo, no imperativo — le decís qué querés, no cómo conseguirlo. Es el cambio mental más grande viniendo de JS. Pensalo como describir el resultado final de un .filter().map() encadenado, pero el motor decide el orden de ejecución real.

1. SELECT básico

SELECT Name, Price
FROM Products
WHERE Price > 100
ORDER BY Price DESC;
SQLEquivalente mental en JS
SELECT Name, Price.map(p => ({ name: p.Name, price: p.Price }))
WHERE Price > 100.filter(p => p.Price > 100)
ORDER BY Price DESC.sort((a, b) => b.Price - a.Price)

2. JOIN: combinar dos tablas por una clave

Un JOIN es exactamente lo que harías en JS para "enriquecer" un array cruzándolo con otro por id:

// JS: cruzar orders con customers por CustomerId
orders.map(o => ({
  ...o,
  customerName: customers.find(c => c.Id === o.CustomerId)?.Name
}));

-- T-SQL equivalente
SELECT o.Id, o.Total, c.Name AS CustomerName
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.Id;
Tipo de JOINQué devuelveEquivalente JS
INNER JOINSolo filas que hacen match en ambas tablas.find() que descarta los undefined
LEFT JOINTodas las filas de la izquierda, con NULL si no hay match a la derecha.find() que conserva el resultado aunque sea undefined
LEFT JOIN es el que más se usa mal en entrevistas: si necesitás "todos los clientes, tengan o no órdenes", es LEFT JOIN desde Customers. Si usás INNER JOIN ahí, perdés los clientes sin órdenes silenciosamente — un bug clásico.

3. Agregaciones: GROUP BY

SELECT CustomerId, COUNT(*) AS OrderCount, SUM(Total) AS TotalSpent
FROM Orders
GROUP BY CustomerId
HAVING SUM(Total) > 1000;
CláusulaQué haceEquivalente JS
GROUP BYAgrupa filas por una columnaObject.groupBy() / reduce en un mapa por clave
COUNT/SUM/AVGAgregan valores dentro de cada grupo.length / .reduce((a,b)=>a+b) por grupo
HAVINGFiltra después de agrupar (WHERE filtra antes).filter() aplicado al resultado ya agrupado
Orden lógico de ejecución (no el orden en que lo escribís): FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Por eso WHERE no puede filtrar por un alias definido en SELECT, pero ORDER BY sí puede.

4. Stored procedures

Un stored procedure es como una función exportada que vive dentro de la base de datos: recibe parámetros, ejecuta T-SQL, opcionalmente retorna un result set.

CREATE PROCEDURE GetOrdersByCustomer
    @CustomerId INT,
    @MinTotal DECIMAL(10,2) = 0        -- parámetro opcional con default
AS
BEGIN
    SELECT Id, Total, OrderDate
    FROM Orders
    WHERE CustomerId = @CustomerId
      AND Total >= @MinTotal
    ORDER BY OrderDate DESC;
END;

-- Ejecutarlo:
EXEC GetOrdersByCustomer @CustomerId = 42, @MinTotal = 100;
PiezaNota
@CustomerIdLos parámetros siempre llevan @ — equivalente a un parámetro de función
AS BEGIN ... ENDEl cuerpo del "función" — puede tener múltiples statements, variables, lógica condicional
¿Por qué usarlos?Reutilización, seguridad (evita SQL injection al parametrizar), y a veces mejor performance porque el plan de ejecución se cachea

Ejercicio práctico

Sin mirar arriba: escribí un stored procedure GetTopCustomers que reciba un parámetro @MinOrders INT y devuelva CustomerId y la cantidad de órdenes, solo para clientes con al menos @MinOrders órdenes, ordenado de mayor a menor cantidad.

Compará tu respuesta antes de seguir.

CREATE PROCEDURE GetTopCustomers
    @MinOrders INT
AS
BEGIN
    SELECT CustomerId, COUNT(*) AS OrderCount
    FROM Orders
    GROUP BY CustomerId
    HAVING COUNT(*) >= @MinOrders
    ORDER BY OrderCount DESC;
END;
