Async vs multithreading: lo que puede salir como pregunta conceptual

Objetivo: explicar con criterio la diferencia entre async/await y multithreading real, y saber cuándo usar cada uno. Esto no está en el posting explícitamente — es vocabulario típico de "Sr." que puede salir en la entrevista conceptual, no en la prueba práctica. Prioridad menor a las lecciones anteriores.

1. El malentendido más común: async no siempre es "otro hilo"

Ya usaste async/await en cada endpoint (await _context.Products.ToListAsync()). La pregunta de entrevista es: ¿ese await crea un thread nuevo? No, no necesariamente.

Microsoft lo distingue así: "I/O-bound code starts an operation represented by a Task... CPU-bound code starts an operation on a background thread with the Task.Run method." — Un query a SQL Server es I/O-bound: tu código le pide el dato a la red y libera el thread mientras espera la respuesta, no lo bloquea ni gasta un thread extra. Task.Run es distinto: agarra un thread del thread pool para correr algo que sí necesita CPU real (un cálculo pesado), no red ni disco.

Es la misma idea que el await de JS con fetch() — no bloquea el event loop mientras espera la red. La diferencia real: JS es single-threaded siempre (un solo hilo, el event loop). C# tiene un thread pool real detrás — Task.Run sí puede usar un segundo hilo físico cuando el trabajo lo justifica.

2. Cuándo usar cada uno

PreguntaEscenarioQué usar
¿Esperás una respuesta externa (DB, HTTP, archivo)?I/O-boundasync/await directo — sin Task.Run
¿Corrés un cálculo pesado en CPU?CPU-boundasync/await + Task.Run para no bloquear el thread que llama

Error común en la práctica: envolver un await _context.Products.ToListAsync() (ya I/O-bound, ya asíncrono) dentro de un Task.Run(() => ...) — no gana nada, solo gasta un thread del pool para no hacer nada mientras espera igual.

3. Esperar varias tareas en paralelo: Task.WhenAll

Cuando necesitás varios datos independientes (ej. un dashboard que pide Customers y Products a la vez), lanzarlos secuencialmente con await uno tras otro suma sus tiempos. Task.WhenAll los corre en paralelo y espera a que terminen todos:

// Secuencial — el tiempo total es la SUMA de ambos
var customers = await _customerRepository.GetAllAsync();
var products = await _productRepository.GetAllAsync();

// Paralelo — el tiempo total es el MÁS LENTO de los dos, no la suma
var customersTask = _customerRepository.GetAllAsync();
var productsTask = _productRepository.GetAllAsync();
await Task.WhenAll(customersTask, productsTask);

var customers = await customersTask;
var products = await productsTask;
Esto funciona para dos queries independientes. No funciona si ambas comparten el mismo DbContext — ver el punto 4.

4. El gotcha real de tu proyecto: DbContext no es thread-safe

AddScoped<TuDbContext>() (lección 4) te da una instancia por request, nunca compartida entre requests distintos — eso ya te protege del caso general. Pero si alguna vez lanzás dos queries en paralelo dentro del mismo request usando el mismo _context (ej. dos Task.WhenAll contra el mismo DbContext), vas a tener una excepción en runtime: EF Core no permite dos operaciones concurrentes sobre la misma instancia. Si necesitás paralelismo real dentro de un mismo endpoint, cada tarea necesita su propio DbContext (o simplemente no paralelizar esa parte — para la mayoría de endpoints CRUD, secuencial alcanza).

5. Race conditions y lock (solo para reconocerlo)

Una race condition pasa cuando dos threads leen y escriben la misma variable compartida sin coordinación, y el resultado final depende de qué thread "ganó la carrera". lock es la herramienta básica de C# para evitarlo:

private readonly object _lock = new();
private int _counter = 0;

public void Increment()
{
    lock (_lock)
    {
        _counter++;   // solo un thread a la vez puede estar acá adentro
    }
}

En una Web API típica esto casi no aparece (cada request tiene su propio scope, no comparte estado mutable) — pero es la respuesta esperada si te preguntan "¿qué es una race condition y cómo la evitás en C#?".

Resumen para la entrevista

Si te preguntan "¿cuándo usarías Task.Run vs. simplemente await?": "await directo para trabajo I/O-bound como una query o un HTTP call, porque libera el thread mientras espera. Task.Run solo para trabajo CPU-bound, porque ahí sí necesito correr algo en paralelo real. Y si necesito varias tareas independientes a la vez, Task.WhenAll en vez de encadenar awaits secuenciales."
