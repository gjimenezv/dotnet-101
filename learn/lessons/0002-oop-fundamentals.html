Clases, constructores y OOP en C#

Objetivo: recordar cómo se arma una clase — constructor, modificadores de acceso, interfaces, clases abstractas, herencia — porque todo lo que viene (controllers, DI, EF Core) es esto.

C# es un lenguaje orientado a objetos "de verdad": no hay forma de escribir código fuera de una clase. JS te dejaba usar objetos, funciones sueltas o clases como te convenga; C# te obliga a pensar en términos de clases, contratos (interfaces) y jerarquías. Vale la pena fijar esto bien porque el controller y la inyección de dependencias de las próximas lecciones son, literalmente, esto en acción.

1. Anatomía de una clase

public class User
{
    // campos/propiedades — el "shape" del objeto
    public string Name { get; set; }
    public string Email { get; set; }

    // constructor — se ejecuta al hacer "new User(...)"
    public User(string name, string email)
    {
        Name = name;
        Email = email;
    }

    // método — comportamiento
    public string GetGreeting()
    {
        return $"Hola, {Name}";
    }
}

var user = new User("Gabriela", "gabi@mail.com");   // llama al constructor
Console.WriteLine(user.GetGreeting());

2. El constructor, en detalle

El constructor es un método especial con el mismo nombre que la clase, sin tipo de retorno, que corre una sola vez cuando creás el objeto con new. Es el equivalente directo del constructor() de una clase de JS/TS.

JS/TSC#
class User { constructor(name) { this.name = name; } }public User(string name) { Name = name; }
this.namethis.Name (o simplemente Name si no hay ambigüedad)
Si no escribís ningún constructor, C# te da uno vacío gratis ("default constructor", sin parámetros). Pero en cuanto definís un constructor con parámetros, ese regalo desaparece — si todavía querés poder hacer new User() sin argumentos, tenés que escribirlo vos, explícitamente, además del otro. Podés tener varios constructores con distinta cantidad/tipo de parámetros (overloading). 
public class User
{
    public string Name { get; set; }

    public User() { Name = "Anónimo"; }              // constructor sin parámetros
    public User(string name) { Name = name; }          // constructor con parámetro
}

3. Modificadores de acceso

Determinan quién puede ver/usar un miembro de la clase — el equivalente de public/private de TS, pero con más granularidad.

ModificadorQuién puede acceder
publicCualquiera, desde cualquier lugar
privateSolo desde dentro de la misma clase (default si no ponés nada)
protectedLa misma clase, y cualquier clase que herede de ella
internalCualquier clase dentro del mismo proyecto/assembly, pero no desde otro proyecto
protected internalUnión de protected e internal
TS solo tiene public/private/protected, y esos modificadores desaparecen al compilar a JS (son una ficción del compilador). En C# son reales: el CLR los aplica en tiempo de ejecución — no hay forma de acceder a un private desde afuera, ni con trucos.

4. Interfaces: un contrato, sin implementación

Una interfaz define qué métodos/propiedades debe tener una clase, sin decir cómo los implementa. Convención: el nombre empieza con I.

public interface IPaymentProcessor
{
    Task<bool> ProcessAsync(decimal amount);
}

public class CreditCardProcessor : IPaymentProcessor
{
    public async Task<bool> ProcessAsync(decimal amount)
    {
        // implementación real acá
        return true;
    }
}

Una clase puede implementar varias interfaces a la vez (a diferencia de la herencia de clases, que es de una sola). Esto es exactamente lo que viste en la lección de Web API: IProductService/ProductService es este mismo patrón — el controller depende de la interfaz, no de la clase concreta, y el contenedor de DI decide qué implementación inyectar.

5. Clases abstractas: a mitad de camino

Una clase abstract no se puede instanciar directamente (new falla) — existe solo para que otras clases hereden de ella. Puede mezclar métodos ya implementados con métodos abstract que las clases hijas están obligadas a completar.

public abstract class Shape
{
    public abstract double GetArea();            // sin cuerpo — obligatorio implementarlo

    public void PrintArea()                        // con cuerpo — se hereda tal cual
    {
        Console.WriteLine($"Área: {GetArea()}");
    }
}

public class Circle : Shape
{
    public double Radius { get; set; }
    public override double GetArea() => Math.PI * Radius * Radius;
}
InterfaceAbstract class
ImplementaciónNinguna (solo firma)Puede tener métodos ya implementados
Herencia múltipleUna clase implementa variasUna clase hereda de una sola
Estado (campos)NoSí, puede tener campos/propiedades con valor
Cuándo usarlaDefinir un contrato entre capas (ej. service ↔ controller)Compartir código común entre clases muy relacionadas

6. Herencia: extender una clase

public class Animal
{
    public string Name { get; set; }

    public Animal(string name) { Name = name; }

    public virtual string MakeSound() => "...";   // "virtual" = se puede sobreescribir
}

public class Dog : Animal
{
    public Dog(string name) : base(name) { }        // llama al constructor del padre

    public override string MakeSound() => "Woof";   // sobreescribe el comportamiento
}
Palabra claveQué hace
: Animal"Dog hereda de Animal" — equivalente a class Dog extends Animal en JS
: base(name)Llama al constructor de la clase padre — equivalente a super(name)
virtualEn el padre: "esto se puede sobreescribir"
overrideEn el hijo: "estoy sobreescribiendo esto"
C# solo permite herencia simple: una clase hereda de una sola clase base (a diferencia de interfaces, donde podés implementar varias). Si necesitás combinar comportamiento de múltiples fuentes, usá interfaces.

Retrieval practice
