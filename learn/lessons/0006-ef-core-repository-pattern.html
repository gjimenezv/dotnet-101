Entity Framework Core y el repository pattern

Objetivo: entender DbContext/DbSet, leer/escribir datos con LINQ, configurar el modelo con Fluent API, y poder explicar con criterio cuándo (y por qué) agregar una capa de repository encima.

Esta lección conecta las piezas anteriores: los DTOs de la lección 3, el LINQ que adelantamos en la lección 1, y las tablas de la lección 5 — EF Core es la capa que las une.

1. ¿Qué es EF Core?

Un ORM (Object-Relational Mapper): traduce clases de C# a tablas SQL y viceversa, para que escribas LINQ en vez de T-SQL a mano en tu código de aplicación. Es similar a lo que Prisma o TypeORM hacen en el mundo Node — si conocés alguno, la mecánica mental es la misma.

public class AppDbContext : DbContext
{
    public DbSet<Product> Products { get; set; }
    public DbSet<Order> Orders { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Product>()
            .Property(p => p.Price)
            .HasColumnType("decimal(10,2)");
    }
}

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}
ConceptoQué es
DbContextLa conexión + sesión de trabajo con la base de datos — se registra en DI como AddScoped (una instancia por request, igual que vimos en la lección 2)
DbSet<T>Representa una tabla; permite consultarla y modificarla con LINQ
OnModelCreatingMétodo que EF Core llama para armar el "mapa" completo clase↔tabla — acá van las reglas que no entran como una simple propiedad de C#
Migrationsdotnet ef migrations add InitialCreate genera el script de cambios; dotnet ef database update lo aplica — el equivalente a un sistema de migraciones tipo Prisma/Knex
OnModelCreating es donde vive la Fluent API — la forma de configurar EF Core con código en vez de atributos sobre las propiedades. Se ejecuta una sola vez, la primera vez que tu app usa el DbContext (no en cada request, no en cada query) — EF Core arma el modelo completo, lo cachea en memoria, y lo reusa. Pensalo como un schema de Prisma o de Mongoose: no describe una query puntual, describe las reglas permanentes de cómo tus clases se convierten en tablas. Ahí configurás lo que una propiedad simple no puede expresar: precisión de un decimal, qué pasa al borrar en una relación (OnDelete), claves compuestas, índices, conversiones de tipo, datos semilla (HasData). Todo lo que hicimos con modelBuilder en esta lección y en la lección 7 vive acá adentro, en un solo método.

Otras reglas comunes que también van en OnModelCreating — mismo flujo siempre: cambiás esto, generás una migración nueva, la aplicás.

Necesitás...Cómo
ÍndicemodelBuilder.Entity<Product>().HasIndex(p => p.Name); — EF Core ya indexa automático cualquier columna FK, esto es para las que no lo son
FK que la convención no adivinaMismo patrón que Employee.Manager: .HasOne(o => o.ProcessedBy).WithMany().HasForeignKey(o => o.ProcessedByEmployeeId);
Clave primaria compuestamodelBuilder.Entity<OrderItem>().HasKey(oi => new { oi.OrderId, oi.ProductId }); — EF Core solo detecta un Id simple por convención, una compuesta siempre se declara a mano
No todo cambio toca las dos cosas. Un campo simple (string, int, bool) nuevo en el modelo, EF Core lo infiere solo — no necesita nada en OnModelCreating. Un índice sobre un campo que ya existe, al revés: solo OnModelCreating, no tocás la clase. Lo que sí es siempre igual, sin excepción, es lo de después: dotnet ef migrations add NombreDescriptivo y dotnet ef database update — ningún cambio de schema llega a la base sin pasar por esos dos comandos.

2. LINQ to Entities: tu .filter()/.map() ahora hablan SQL

Lo que en la lección 1 vimos como analogía, acá es literal: EF Core traduce estas expresiones LINQ a SQL real, ejecutado en el servidor — no en memoria.

// Trae solo productos caros, ordenados — se traduce a un SELECT ... WHERE ... ORDER BY real
var expensiveProducts = await _context.Products
    .Where(p => p.Price > 100)
    .OrderByDescending(p => p.Price)
    .ToListAsync();

// JOIN implícito vía navegación de propiedades
var ordersWithCustomer = await _context.Orders
    .Include(o => o.Customer)          // como un LEFT JOIN explícito
    .Where(o => o.Status == "Shipped")
    .ToListAsync();
.Where() antes de .ToListAsync() se ejecuta en la base de datos (SQL real). Si llamás .ToList() primero y filtrás después, estás trayendo toda la tabla a memoria y filtrando en C# — un error de performance clásico que sí te pueden preguntar en la prueba.

3. CRUD con EF Core

// Create
_context.Products.Add(new Product { Name = "Mouse", Price = 25.99m });
await _context.SaveChangesAsync();

// Update — EF trackea el cambio automáticamente
var product = await _context.Products.FindAsync(id);
product.Price = 19.99m;
await _context.SaveChangesAsync();

// Delete
_context.Products.Remove(product);
await _context.SaveChangesAsync();

SaveChangesAsync() es la clave: EF Core acumula cambios en memoria (tracking) y los aplica todos juntos en una transacción cuando lo llamás — no hay un statement SQL por cada línea de C#.

4. Repository pattern: ¿encima de EF Core, o no?

Acá viene la pregunta que más se presta a confusión — y la que probablemente te van a hacer en la entrevista.

Microsoft aclara algo importante en su propia documentación: EF Core ya implementa Repository y Unit of Work internamente. DbContext es tu Unit of Work; cada DbSet<T> es, en esencia, un Repository. Envolver eso en tu propia interfaz IProductRepository no es "la forma correcta", es una decisión de trade-off.
Agregar una capa repository propiaUsar DbContext/DbSet directo
Más fácil de mockear en tests unitarios sin base de datos realMenos código, menos indirección — más simple de leer
Aísla tu dominio de detalles de EF Core (útil si algún día cambiás de ORM)Acceso completo a LINQ y features de EF Core sin fricción
Tiene sentido en apps grandes/complejas con lógica de acceso a datos repetidaTiene sentido en apps chicas/medianas o cuando el equipo ya usa EF Core como su capa de abstracción

Ejemplo de repository pattern clásico, para reconocerlo si aparece en la prueba:

public interface IProductRepository
{
    Task<Product?> GetByIdAsync(int id);
    Task<List<Product>> GetAllAsync();
    Task AddAsync(Product product);
}

public class ProductRepository : IProductRepository
{
    private readonly AppDbContext _context;
    public ProductRepository(AppDbContext context) => _context = context;

    public Task<Product?> GetByIdAsync(int id) =>
        _context.Products.FirstOrDefaultAsync(p => p.Id == id);

    public Task<List<Product>> GetAllAsync() =>
        _context.Products.ToListAsync();

    public async Task AddAsync(Product product)
    {
        _context.Products.Add(product);
        await _context.SaveChangesAsync();
    }
}

Y se registra en DI exactamente como el IProductService de la lección 2: builder.Services.AddScoped<IProductRepository, ProductRepository>();

Checkpoint del proyecto

En tu propio proyecto (el que creaste en la lección 4): escribí el modelo Category y agregalo a tu DbContext, como ejemplo de punta a punta:

// Models/Category.cs
public class Category
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;
    public ICollection<Product> Products { get; set; } = new List<Product>();
}

// Data/TuDbContext.cs
public class TuDbContext : DbContext
{
    public TuDbContext(DbContextOptions<TuDbContext> options) : base(options) { }

    public DbSet<Category> Categories => Set<Category>();
}

Ahora hacé lo mismo vos para Product, Customer, Order, OrderItem y Employee — con sus campos y relaciones según la definición del proyecto. Todavía no corras dotnet ef migrations add: ese comando es el tema completo de la próxima lección.
