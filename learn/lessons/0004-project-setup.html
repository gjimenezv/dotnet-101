Creando tu proyecto desde cero y conectándolo a SQL Server

Objetivo: crear tu propio proyecto ASP.NET Core con la CLI (no un scaffold que te doy armado), y dejarlo hablando con una base SQL Server real.

Hasta acá viste conceptos (lecciones 1-2) y sintaxis de controllers/DI (lección 3) sin un proyecto real corriendo. Esta lección es el primer paso 100% práctico: vos vas a crear el proyecto, vos vas a instalar los paquetes, vos vas a escribir la connection string. Yo no voy a tocar tu carpeta — este documento es la referencia, no el resultado.

1. Crear el proyecto con la CLI

Elegí un nombre y una carpeta (por ejemplo /home/asd/dev/TuProyecto) y corré:

cd /home/asd/dev
dotnet new webapi -n TuProyecto --use-controllers -o TuProyecto
cd TuProyecto
dotnet build
FlagQué hace
webapiTemplate de Web API — genera Program.cs, appsettings.json, un controller de ejemplo
-nNombre del proyecto (define el namespace raíz)
--use-controllersUsa controllers clásicos (lección 3), no Minimal API
-oCarpeta de salida

Si dotnet build termina en "Build succeeded" ya tenés un Web API funcional, aunque todavía no haga nada útil. Ese es el checkpoint de este paso.

2. Agregar los paquetes de EF Core

El template no trae Entity Framework — hay que agregarlo vos, como agregarías una dependencia con npm install:

dotnet add package Microsoft.EntityFrameworkCore.SqlServer
dotnet add package Microsoft.EntityFrameworkCore.Design
PaquetePara qué sirve
Microsoft.EntityFrameworkCore.SqlServerEl "driver"/provider — le dice a EF Core cómo hablar con SQL Server específicamente (existe uno distinto por motor de base de datos)
Microsoft.EntityFrameworkCore.DesignHerramientas de diseño — necesario para que dotnet ef migrations add funcione (lección 7)

3. La base de datos: ya existe, no necesitás instalar nada

Para esta prueba de concepto ya hay una instancia de SQL Server 2022 real corriendo en un container Docker en esta máquina (shopapi-sqlserver, puerto 1433). No necesitás instalar SQL Server ni saber Docker — eso no es parte de lo que pide el puesto. Lo único que te toca a vos es la connection string, que es una habilidad C#/.NET real.

DatabaseElegí un nombre propio (ej. TuProyectoDb) — EF Core la crea sola cuando corras tu primera migración en la lección 7. No uses ShopApi, ese nombre ya tiene datos de un proyecto de referencia.

4. La connection string

Va en appsettings.json, bajo una sección ConnectionStrings — el equivalente a una variable en tu .env, pero en JSON y con nombre:

{
  "ConnectionStrings": {
    "Default": "Server=localhost,1433;Database=TuProyectoDb;User Id=sa;Password=Interview2026!Study;TrustServerCertificate=True"
  }
}

TrustServerCertificate=True es necesario porque el container usa un certificado autofirmado — en producción real esto se maneja distinto (certificado válido), pero para desarrollo local es estándar.

5. Registrar el DbContext en Program.cs

Todavía no tenés un DbContext propio (eso es la lección 6), pero así se ve el cableado — es el mismo patrón de AddScoped que ya viste en la lección 3, EF Core lo hace por vos con un método especializado:

using Microsoft.EntityFrameworkCore;

builder.Services.AddDbContext<TuDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

Esto no va a compilar todavía porque TuDbContext no existe — normal, lo creás en la lección 6. Guardá este patrón, lo vas a pegar tal cual cuando llegues ahí.

Checkpoint del proyecto

Antes de seguir a la lección 5, deberías tener:

  • Un proyecto propio creado con dotnet new webapi, que compila.
  • Los dos paquetes de EF Core agregados (verificalo abriendo tu .csproj).
  • Tu connection string en appsettings.json, con un nombre de base de datos propio.
Si dotnet build te tira un error de paquetes incompatibles (versión de EF Core vs. versión del SDK), pegame el error exacto — es un problema común y rápido de diagnosticar.
