Lección 9 de 12

Cuando LINQ no alcanza: SQL crudo, stored procedures y agregaciones anidadas

Objetivo: saber cuándo bajar de LINQ a SQL crudo o a un stored procedure sin perder la infraestructura de EF Core, y resolver el caso más común de la prueba práctica — un total que no está guardado, hay que calcularlo.

Esta lección asume que ya tenés tu DbContext con las 6 entidades (lección 7) y las migraciones aplicadas contra una base real (lección 8) — todo lo de acá se prueba contra datos reales, no en abstracto. Si ya escribiste los ejercicios de la lección 6, vas a reconocer el mismo SQL, ahora embebido en C#.

1. Cuándo LINQ no alcanza: SQL crudo y stored procedures

LINQ cubre la mayoría de los casos, pero hay cosas que no puede expresar: recursión (CTEs recursivos), window functions (RANK() OVER (PARTITION BY...)), o llamar un stored procedure ya existente. Para eso EF Core te deja bajar a SQL crudo sin perder el resto de la infraestructura (DI, DbContext, tracking).

MétodoPara quéDevuelve
FromSqlRaw / FromSqlInterpolatedSELECT que mapea a un tipo (entidad o keyless) — sigue siendo IQueryable, se puede encadenar más LINQ despuésFilas tipadas
ExecuteSqlRawAsync / ExecuteSqlInterpolatedAsyncINSERT/UPDATE/DELETE, o un EXEC que no devuelve filasint (filas afectadas)
Usá siempre FromSqlInterpolated (con $"...") o pasá los parámetros como argumentos extra de FromSqlRaw — nunca concatenés el valor directo en el string. EF Core parametriza automáticamente en ambos casos; concatenar a mano te expone a SQL injection, el mismo error que en cualquier otro lenguaje.

Caso 1 — el resultado es una entidad completa (ej. productos con precio mayor a X): es directo, porque las columnas calzan 1 a 1 con tu clase Product.

var caros = await _context.Products
    .FromSqlInterpolated($"SELECT * FROM Products WHERE Price > {minPrice}")
    .ToListAsync();

Caso 2 — el resultado NO es una entidad (ej. el stored procedure GetTopCustomers de la lección 5 devuelve CustomerId + OrderCount, no un Customer completo). Necesitás un tipo "keyless" — una clase sin PK, registrada en el modelo solo para mapear ese resultado:

// Un DTO simple, sin Id
public class TopCustomerResult
{
    public int CustomerId { get; set; }
    public int OrderCount { get; set; }
}

// En OnModelCreating de tu DbContext:
modelBuilder.Entity<TopCustomerResult>().HasNoKey();

// En el repository:
var top = await _context.Database
    .SqlQueryRaw<TopCustomerResult>("EXEC GetTopCustomers @MinOrders = {0}", minOrders)
    .ToListAsync();

Fuente: Querying with raw SQL in EF Core — Microsoft Learn.

2. Queries anidadas: cuando el dato no está guardado, hay que calcularlo

Fijate en el schema de la definición del proyecto: Order no tiene un campo Total. Es a propósito — guardar un total calculable es duplicar datos que se pueden desincronizar (¿qué pasa si editás un OrderItem y te olvidás de actualizar el total del Order?). El total real sale de sumar Quantity * UnitPrice de cada OrderItem. Esto convierte cualquier query sobre "el total de una orden" en una agregación anidada — un Sum adentro de otro nivel de datos.

Es el mismo patrón que orders.reduce((sum, o) => sum + o.items.reduce((s, i) => s + i.qty * i.price, 0), 0) en JS — un reduce adentro de otro. En LINQ, la versión "sum de sum" se escribe con SelectMany (tu .flatMap()) para aplanar antes de sumar, o directo con .Sum() sobre la navigation property si es un solo nivel.

Nivel 1 — total de una sola orden (un Sum sobre sus Items):

var orderTotals = await _context.Orders
    .Select(o => new
    {
        o.Id,
        o.CustomerId,
        Total = o.Items.Sum(oi => oi.Quantity * oi.UnitPrice)
    })
    .ToListAsync();

Nivel 2 — total de un cliente (todas sus órdenes, cada una con sus items — necesitás aplanar con SelectMany antes de sumar):

var customerTotals = await _context.Customers
    .Select(c => new
    {
        Customer = c,
        Total = c.Orders
            .Where(o => o.Status == "Shipped")
            .SelectMany(o => o.Items)                      // aplana Orders→Items en una sola secuencia
            .Sum(oi => oi.Quantity * oi.UnitPrice)
    })
    .ToListAsync();

Ahora el caso real: clientes con gasto por encima del promedio. Acá el promedio depende de los totales de todos los clientes — no lo podés calcular dentro del mismo Where sin antes tenerlo resuelto. Dos formas válidas:

(a) Dos queries — la forma recomendada, más legible:

var average = await _context.Customers
    .Select(c => c.Orders.Where(o => o.Status == "Shipped")
                          .SelectMany(o => o.Items)
                          .Sum(oi => oi.Quantity * oi.UnitPrice))
    .AverageAsync();

var aboveAverage = await _context.Customers
    .Where(c => c.Orders.Where(o => o.Status == "Shipped")
                         .SelectMany(o => o.Items)
                         .Sum(oi => oi.Quantity * oi.UnitPrice) > average)
    .ToListAsync();
Dos round-trips a la base de datos no es un error de performance acá — es la opción correcta. Cada query es simple, se traduce a SQL predecible, y es fácil de leer/debuggear. Intentar forzarlo en una sola query (ver (b) abajo) gana un round-trip pero pierde legibilidad — en una entrevista, preferí poder explicar por qué elegiste la versión simple antes que mostrar la más "clever".

(b) Una sola query, con el promedio inline — más parecido a la subquery correlacionada de T-SQL que viste en la lección 6. EF Core a veces puede traducir esto a un único SQL con subquery escalar, pero es más frágil (puede fallar la traducción según la versión de EF Core, y es más difícil de leer):

var aboveAverage = await _context.Customers
    .Where(c => c.Orders.Where(o => o.Status == "Shipped")
                         .SelectMany(o => o.Items)
                         .Sum(oi => oi.Quantity * oi.UnitPrice)
                > _context.Customers.Average(c2 =>
                    c2.Orders.Where(o => o.Status == "Shipped")
                             .SelectMany(o => o.Items)
                             .Sum(oi => oi.Quantity * oi.UnitPrice)))
    .ToListAsync();

Ejercicio práctico

Sin mirar arriba: escribí una consulta LINQ contra _context.Orders que devuelva los pedidos de un cliente específico (customerId) cuyo total — calculado desde sus OrderItems, no un campo guardado — sea mayor a 500, ordenados por fecha descendente.

Compará tu respuesta antes de seguir.

var orders = await _context.Orders
    .Where(o => o.CustomerId == customerId
        && o.Items.Sum(oi => oi.Quantity * oi.UnitPrice) > 500)
    .OrderByDescending(o => o.OrderDate)
    .ToListAsync();
