Testear tu Service/Repository sin tocar la base de datos real

Objetivo: crear un proyecto de tests, mockear una dependencia, y escribir un test real contra tu OrderService. El posting dice explícito "code reviews, testing, debugging, performance tuning" — es lo único de esa frase que hasta ahora no practicaste.

Esto es tu Jest/Vitest. xUnit es el test runner (el describe/it). Moq es tu jest.mock() — reemplaza una dependencia real por una falsa que vos controlás.

1. Por qué esto NO toca tu base de datos

Un unit test prueba una unidad de lógica aislada — no una base de datos real, no HTTP real. Tu OrderService (lección 0000, sección 5) es el candidato perfecto: su lógica de negocio (validar que el producto exista, copiar el precio) no depende de SQL Server, solo de las interfaces IProductRepository/IOrderRepository que ya definiste. Si mockeás esas interfaces, podés probar la lógica sin Docker, sin conexión, en milisegundos.

(Un integration test, en cambio, sí golpea una base real — está fuera de alcance para hoy; con esto alcanza para hablar de "testing" con propiedad en la entrevista.)

2. Crear el proyecto de test

Tu proyecto de tests vive separado del proyecto principal, pero lo referencia:

dotnet new xunit -o TuProyecto.Tests
dotnet add ./TuProyecto.Tests reference ./TuProyecto
dotnet add ./TuProyecto.Tests package Moq

dotnet new xunit ya agrega los paquetes de xUnit por vos (Microsoft.NET.Test.Sdk, xunit, xunit.runner.visualstudio). El segundo comando es lo que te deja hacer using TuProyecto.Services; desde el proyecto de tests.

3. Anatomía de un test: [Fact] + Arrange-Act-Assert

using Xunit;

public class CalculatorTests
{
    [Fact]
    public void Add_TwoPositiveNumbers_ReturnsSum()
    {
        // Arrange — preparás los datos/objetos que necesitás
        var a = 2;
        var b = 3;

        // Act — ejecutás lo que estás probando
        var result = a + b;

        // Assert — verificás el resultado
        Assert.Equal(5, result);
    }
}

[Fact] marca un método como un test que corre solo. Nombre del método: convención Método_Escenario_ResultadoEsperado — se lee como una frase.

4. Mockear una dependencia con Moq

Moq crea una implementación falsa de una interfaz en tiempo de ejecución — vos le decís qué devolver cuando se llama a cada método:

var mockProducts = new Mock<IProductRepository>();

// "Cuando alguien llame GetByIdAsync(1), devolvé este Product"
mockProducts
    .Setup(p => p.GetByIdAsync(1))
    .ReturnsAsync(new Product { Id = 1, Name = "Mouse", Price = 25.99m });

// Pasás mock.Object (no el mock en sí) a la clase que estás probando
var service = new OrderService(mockOrders.Object, mockProducts.Object);
Error común: pasar mockProducts directo en vez de mockProducts.Object. El Mock<T> es el controlador del falso; .Object es el objeto falso que efectivamente implementa IProductRepository.

5. Ejemplo real: testeando OrderService.PlaceOrderAsync

Dos casos que valen la pena probar de la lógica que ya escribiste en la sección 5 del roadmap:

public class OrderServiceTests
{
    [Fact]
    public async Task PlaceOrderAsync_ProductDoesNotExist_ThrowsException()
    {
        // Arrange
        var mockProducts = new Mock<IProductRepository>();
        mockProducts.Setup(p => p.GetByIdAsync(It.IsAny<int>()))
                    .ReturnsAsync((Product?)null);   // no existe

        var mockOrders = new Mock<IOrderRepository>();
        var service = new OrderService(mockOrders.Object, mockProducts.Object);

        var request = new CreateOrderRequest
        {
            CustomerId = 1,
            Items = new List<OrderLineRequest> { new() { ProductId = 999, Quantity = 1 } }
        };

        // Act + Assert — InvokeAsync porque esperamos una excepción async
        await Assert.ThrowsAsync<InvalidOperationException>(
            () => service.PlaceOrderAsync(request));
    }

    [Fact]
    public async Task PlaceOrderAsync_ValidProduct_SnapshotsCurrentPrice()
    {
        // Arrange
        var product = new Product { Id = 1, Name = "Mouse", Price = 25.99m };
        var mockProducts = new Mock<IProductRepository>();
        mockProducts.Setup(p => p.GetByIdAsync(1)).ReturnsAsync(product);

        Order? createdOrder = null;
        var mockOrders = new Mock<IOrderRepository>();
        mockOrders.Setup(o => o.CreateAsync(It.IsAny<Order>()))
                  .Callback<Order>(o => createdOrder = o)   // captura lo que le pasaron
                  .ReturnsAsync((Order o) => o);

        var service = new OrderService(mockOrders.Object, mockProducts.Object);
        var request = new CreateOrderRequest
        {
            CustomerId = 1,
            Items = new List<OrderLineRequest> { new() { ProductId = 1, Quantity = 2 } }
        };

        // Act
        await service.PlaceOrderAsync(request);

        // Assert
        Assert.NotNull(createdOrder);
        Assert.Equal(25.99m, createdOrder!.OrderItems.First().UnitPrice);
        mockOrders.Verify(o => o.CreateAsync(It.IsAny<Order>()), Times.Once);
    }
}

El segundo test es el que vale más en una entrevista: no solo corre sin errores, verifica la regla de negocio real (el precio se copia al momento de crear la orden) sin depender de que exista una base de datos con ese producto cargado.

6. Bonus: [Theory] para no repetir el mismo test con distintos inputs

[Theory]
[InlineData(0)]
[InlineData(-1)]
public async Task PlaceOrderAsync_InvalidQuantity_ThrowsException(int quantity)
{
    // mismo test, corre una vez por cada InlineData
}

Fuente principal: Unit testing C# with dotnet test and xUnit — Microsoft Learn. Sintaxis de Moq: Moq Quickstart — repositorio oficial.

Checkpoint del proyecto

Agregá un tercer test vos: verificá que si mandás dos OrderLineRequest distintos, createdOrder.OrderItems tiene exactamente 2 elementos. Es el mismo patrón de Callback + Assert de arriba, cambiando qué revisás.

Retrieval practice

¿Qué diferencia a un unit test de un integration test?

Tenés var mock = new Mock<IProductRepository>();. ¿Qué le pasás al constructor de la clase que estás probando?

¿Qué hace mockOrders.Verify(o => o.CreateAsync(It.IsAny<Order>()), Times.Once);?

Si dotnet add reference te tira un error de que no encuentra el proyecto, o si Assert.ThrowsAsync no compila (versión vieja de xUnit), pegame el error exacto antes de asumir que tu código está mal.
