C# para alguien que ya piensa en JS/TS

Objetivo: en 15 minutos, poder leer y escribir C# básico usando lo que ya sabés de JavaScript/TypeScript como andamiaje.

No vas a aprender C# desde cero — vas a traducir lo que ya sabés. TypeScript y C# comparten padre espiritual (ambos con tipado estático, ambos orientados a objetos, sintaxis de llaves), así que la mayor parte del trabajo es mapear vocabulario, no aprender conceptos nuevos.

Regla general: si algo existe en TypeScript con tipos estrictos, probablemente existe en C# con un nombre parecido. Las diferencias reales están en cómo se ejecuta (compilado a IL + CLR, no borrado a JS) y en que todo vive dentro de una clase.

1. Tipado: de TS a C#

En TS, el tipado es una capa que se borra al compilar a JS ("type erasure"). En C#, el tipado es real en tiempo de ejecución: el compilador y el CLR lo hacen cumplir siempre, no hay "modo JS" de escape.

let x: number = 5int x = 5;Punto y coma obligatorio

2. Todo vive dentro de una clase

En JS podés tener funciones sueltas a nivel de módulo. En C#, casi todo — incluso el Main de entrada — vive dentro de una class. Esto no es opcional, es la razón por la que vas a ver public class Foo { } en todos lados.

// TypeScript
function add(a: number, b: number): number {
  return a + b;
}

// C#
public class MathHelper
{
    public int Add(int a, int b)
    {
        return a + b;
    }
}
ModificadorEquivalente mental en TS
publicexportado, visible desde fuera de la clase
privateprivate en TS — mismo nombre, mismo concepto
staticmétodo/propiedad de la clase, no de la instancia (igual que en JS)

3. Propiedades: el { get; set; } que no existe en TS

En TS escribís getters/setters a mano si los necesitás. En C#, las propiedades son un ciudadano de primera clase — se ven como un campo público pero son azúcar sintáctica sobre un getter/setter:

public class User
{
    public string Name { get; set; }        // como una propiedad pública mutable
    public string Email { get; init; }       // solo se puede setear al crear el objeto
    public int Age { get; private set; }     // se lee desde afuera, se escribe solo desde adentro
}

Vas a ver esto constantemente en DTOs y modelos de Entity Framework — es la forma estándar de definir un "shape" de datos, equivalente a un interface de TS pero con comportamiento real.

4. Async/await: mismo keyword, motor distinto

La sintaxis es casi calcada — eso es la buena noticia.

TypeScriptC#
Promise<T>Task<T>
async function f(): Promise<number>async Task<int> F()
await fetch(url)await httpClient.GetAsync(url)
Promise.all([...])Task.WhenAll(...)
Convención de nombres en C#: cualquier método async termina en Async — GetUserAsync(), no GetUser(). Vas a ver esto todo el tiempo en código .NET real y en la prueba del domingo.

5. using es tu import

// TypeScript
import { UserService } from "./services/user-service";

// C#
using MyApp.Services;

Diferencia clave: using importa un namespace completo (una carpeta lógica de clases), no un archivo específico. No hay equivalente exacto a import { X } from "./file" — el "archivo" es invisible, solo importa a qué namespace pertenece la clase.

6. LINQ: tu .map()/.filter(), con esteroides

Esto se profundiza en la lección de Entity Framework, pero adelantamos el mapeo mental porque lo vas a ver en cualquier código C# de nivel medio:

¿Cuál es la diferencia clave entre el tipado de TypeScript y el de C#? (pensalo antes de revelar)

TypeScript usa tipado estructural que se borra por completo al compilar a JS (no existe en runtime). C# usa tipado nominal que el CLR aplica en tiempo de ejecución — los tipos son reales incluso después de compilar, no hay forma de "engañar" al sistema de tipos como con un as any disfrazado.
