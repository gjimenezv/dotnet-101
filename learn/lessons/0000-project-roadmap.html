5. Services — la única pieza que sí lo necesita

De los 9 endpoints, 8 son un Repository, una operación, sin decisiones que tomar — Controller → Repository directo, como viste en el diagrama de la lección 10. Uno solo junta lógica de negocio real que no es ni un query ni una respuesta HTTP: POST /orders (#5 arriba). Ahí sí va un OrderService entre el Controller y los Repositories.

Qué hace que crear una Order sea distinto de los otros 8 endpoints:

ReglaPor qué no es solo un Repository
Cada ProductId de la request debe existirEs una validación de negocio — decide si la operación completa falla o sigue, no es "traer datos"
OrderItem.UnitPrice se copia del Product.Price vigente al momento de crear la orden, no se referencia en vivoRegla de integridad histórica: si el precio del producto cambia después, las órdenes viejas no deben cambiar de precio con él — por eso UnitPrice existe como columna propia en OrderItem en vez de leerse siempre de Product.Price
La operación toca dos aggregate roots (Product para leer, Order para escribir)Un Repository solo conoce su propio aggregate — coordinar dos es orquestación, no acceso a datos
public interface IOrderService
{
    Task<Order> PlaceOrderAsync(CreateOrderRequest request);
}

public class OrderService : IOrderService
{
    private readonly IOrderRepository _orders;
    private readonly IProductRepository _products;

    public OrderService(IOrderRepository orders, IProductRepository products)
    {
        _orders = orders;
        _products = products;
    }

    public async Task<Order> PlaceOrderAsync(CreateOrderRequest request)
    {
        var items = new List<OrderItem>();

        foreach (var line in request.Items)
        {
            var product = await _products.GetByIdAsync(line.ProductId)
                ?? throw new InvalidOperationException($"Product {line.ProductId} no existe");

            items.Add(new OrderItem
            {
                ProductId = product.Id,
                Quantity = line.Quantity,
                UnitPrice = product.Price // snapshot, no referencia en vivo
            });
        }

        var order = new Order
        {
            CustomerId = request.CustomerId,
            OrderDate = DateTime.UtcNow,
            Status = "Pending",
            OrderItems = items
        };

        return await _orders.CreateAsync(order);
    }
}

Registro en Program.cs, igual que un repository: builder.Services.AddScoped<IOrderService, OrderService>();. El OrdersController queda finito: recibe el DTO, llama a _orderService.PlaceOrderAsync(request), devuelve 201 Created — no sabe nada de precios ni de productos.

Los otros 8 endpoints no ganan nada metiendo un Service de por medio — son un Repository, una operación, sin reglas que decidir. Meter un Service en cada endpoint "porque sí" es el mismo error dogmático que el callout de la lección 10 señala para repositories: se vuelve boilerplate sin propósito. La pregunta que decide (paralela a la de aggregate root en repositories): "¿esta operación coordina más de un repository, o decide algo que no es una query?" Si no, Controller → Repository directo alcanza.
