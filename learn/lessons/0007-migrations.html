Lección 7 de 10

Migraciones de EF Core, de una entidad a las seis

Objetivo: generar y aplicar tu primera migración con una sola entidad de ejemplo, y después repetir el proceso vos solo para el resto del schema.

En la lección 6 viste qué es DbContext/DbSet conceptualmente. Acá va el paso que faltaba: cómo esas clases C# se convierten en tablas reales dentro de tu base de datos.

1. Qué es una migración

Una migración es un archivo C# generado automáticamente que describe el cambio entre el estado anterior de tu modelo y el estado nuevo, traducido a instrucciones SQL (CREATE TABLE, ALTER TABLE...). Es el mismo concepto que una migración de Prisma o Django, pero el archivo generado es C#, no SQL crudo ni JSON.

Herramienta de CLI: dotnet-ef. En este entorno ya está instalada (dotnet tool list --global la muestra); en un entorno nuevo se instala con dotnet tool install --global dotnet-ef.

2. Ejemplo completo: una sola entidad, de punta a punta

Vamos a hacer Category completa — copiá el patrón para el resto vos.

Paso 1 — el modelo (Models/Category.cs):

namespace TuProyecto.Models;

public class Category
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;
}

Paso 2 — agregarla al DbContext (el que creaste en la lección 6):

public class TuDbContext : DbContext
{
    public TuDbContext(DbContextOptions<TuDbContext> options) : base(options) { }

    public DbSet<Category> Categories => Set<Category>();
}

Paso 3 — generar la migración:

dotnet ef migrations add InitialCreate

Esto crea 3 archivos en Migrations/:

ArchivoQué contiene
<timestamp>_InitialCreate.csMétodos Up() (qué SQL correr para aplicar el cambio) y Down() (cómo deshacerlo)
<timestamp>_InitialCreate.Designer.csMetadata interna de EF Core sobre el modelo en ese punto — no lo edites a mano
TuDbContextModelSnapshot.cs"Foto" completa del modelo actual — EF Core la usa para calcular el diff la próxima vez que generes una migración

Paso 4 — aplicarla a la base de datos real:

dotnet ef database update

Esto ejecuta el Up() de todas las migraciones pendientes contra la base de datos de tu connection string (lección 4) — si la base de datos todavía no existe, EF Core la crea sola.

Verificá que la tabla se creó de verdad — no confíes solo en "no tiró error". Podés conectarte con cualquier cliente de SQL Server, o desde la terminal: docker exec shopapi-sqlserver /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P 'Interview2026!Study' -C -d TuProyectoDb -Q "SELECT * FROM Categories".
Una vez que tu migración crea las tablas, necesitás datos para probar tus endpoints. No pierdas tiempo inventando filas a mano: /home/asd/dev/ShopApi-reference-solution/seed-data.sql tiene INSERTs listos (T-SQL, con SET IDENTITY_INSERT) para las 6 entidades, mismo dataset que la lección 8. Es solo datos — vos seguís siendo quien crea el modelo y corre la migración; esto simplemente te ahorra tipear 60 filas de prueba.

3. Ahora el resto — a vos

Repetí el ciclo (modelo → agregar a DbSet → migrations add → database update) para Product, Customer, Order, OrderItem y Employee, según el schema de la definición del proyecto. No hace falta una migración por entidad — agrupalas como tenga sentido (por ejemplo, Category+Product juntas porque están relacionadas). Dos cosas te van a dar problemas si no las anticipás:

ProblemaCausaSolución
Warning sobre decimal sin precisiónSQL Server necesita saber cuántos decimales guardar (a diferencia de REAL en SQLite)En OnModelCreating: modelBuilder.Entity<Product>().Property(p => p.Price).HasPrecision(10, 2);
Error "may cause cycles or multiple cascade paths" al migrar EmployeeEmployee tiene una FK a sí misma (ManagerId) — el borrado en cascada por default es ambiguo ahíEn OnModelCreating: configurá esa relación con .OnDelete(DeleteBehavior.Restrict)
Por default, EF Core configura las relaciones requeridas como Cascade: borrás el padre, la base borra los hijos automáticamente. Para Employee.ManagerId, "el padre" y "el hijo" son la misma tabla — al generar el DDL, SQL Server directamente rechaza crear esa FK con cascada automática, porque un borrado en cascada que apunta a sí misma puede formar un ciclo ambiguo (por eso el error sale al migrar, no al borrar). DeleteBehavior.Restrict le dice a EF Core que no pida cascada — la FK se crea igual, pero sin ON DELETE CASCADE. La consecuencia real: si intentás borrar un Employee que todavía tiene gente reportándole (otras filas con ManagerId apuntando a su Id), la base rechaza el DELETE con un error de constraint — tenés que reasignar o borrar primero a sus reports. Es el comportamiento correcto para un organigrama: no querés que borrar un manager borre en cadena a todo su equipo.

4. Cambiar el modelo después: una migración nueva

Este es el flujo que más vas a usar en el día a día — y el más probable de aparecer en la prueba práctica: agregás/cambiás una propiedad, generás otra migración (nunca edites una ya aplicada):

// agregaste esto a Product.cs
public string? Description { get; set; }

dotnet ef migrations add AddedProductDescription
dotnet ef database update

5. Deshacer

ComandoCuándo usarlo
dotnet ef migrations removeLa última migración todavía NO se aplicó a la base de datos — la borra limpio
dotnet ef database update NombreMigracionAnteriorYa se aplicó, pero querés volver atrás — revierte hasta esa migración (ejecuta los Down() de las posteriores)
