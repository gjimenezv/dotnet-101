No hay "session" en una Web API — hay tokens

Objetivo: entender por qué una Web API no guarda sesión en el servidor, cómo leer un token en cada request, proteger un endpoint con [Authorize], y probarlo local sin armar un sistema de login. No está en el posting explícito — lo agrego porque preguntaste vos, pero calculá tiempo: las lecciones 1-11 cubren todo lo que sí está confirmado en el posting.

1. Por qué no hay "session" tradicional acá

Si venís de Express, quizás usaste express-session o cookie-session: el servidor guarda un estado ("este usuario está logueado") y se lo recuerda al cliente con una cookie. Una Web API REST típica no hace eso — es stateless: el servidor no recuerda nada entre requests. Cada request tiene que probar quién es, de nuevo, cada vez.

En vez de una cookie de sesión que el servidor busca en su propia memoria/base, el cliente manda un token (un JWT, casi siempre) en el header Authorization: Bearer <token> de cada request. El token es autocontenido — el servidor no necesita ir a buscar nada a ningún lado para saber quién sos, solo verifica la firma del token. Es la razón por la que las Web APIs escalan mejor: no hay estado de sesión que sincronizar entre instancias del servidor.

2. Configurar autenticación por JWT

dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer

En Program.cs:

builder.Services.AddAuthentication("Bearer").AddJwtBearer();
builder.Services.AddAuthorization();

var app = builder.Build();

app.UseAuthentication();   // ← quién sos
app.UseAuthorization();    // ← qué podés hacer
El orden importa: UseAuthentication siempre va antes que UseAuthorization — no podés decidir si alguien tiene permiso (authorization) antes de saber quién es (authentication). Revisá tu Program.cs real: si generaste el proyecto con la plantilla de ASP.NET Core, probablemente ya tenga app.UseAuthorization() puesto por default — pero sin AddAuthentication()/AddJwtBearer() registrado arriba y sin UseAuthentication() en el pipeline, ese [Authorize] no tiene ninguna identidad real para evaluar.

3. Proteger un endpoint: [Authorize]

[ApiController]
[Route("/api/[controller]")]
public class OrdersController : ControllerBase
{
    [Authorize]
    [HttpGet("mine")]
    public IActionResult GetMyOrders()
    {
        var name = User.Identity?.Name;
        return Ok($"Órdenes de {name}");
    }
}

Sin [Authorize], cualquiera pega al endpoint sin credenciales. Con [Authorize], ASP.NET Core devuelve 401 Unauthorized automático si no viene un token válido en el header — no escribís ese chequeo a mano, es el mismo mecanismo que ya viste con la validación automática de [ApiController].

También se puede proteger el ControllerBase completo poniendo [Authorize] arriba de la clase, y usar [AllowAnonymous] en la acción puntual que sí debe quedar pública (por ejemplo, un endpoint de login).

4. Leer datos del usuario actual adentro del endpoint

ControllerBase.User es un ClaimsPrincipal — la identidad ya decodificada del token, disponible en cualquier action sin que la pidas por parámetro:

var name = User.Identity?.Name;
var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
var isAdmin = User.IsInRole("Admin");

Un claim es un par clave-valor que viaja adentro del token (ej. sub/id de usuario, role, email) — quien firmó el token decidió qué claims incluir. User.FindFirst(...) busca uno específico.

5. Probarlo local sin armar login

No necesitás un sistema de login real para probar esto hoy. El SDK de .NET trae una herramienta para generar tokens válidos de desarrollo:

dotnet user-jwts create

Esto genera un JWT firmado y actualiza appsettings.Development.json con la configuración necesaria para que tu propio proyecto lo acepte. Copiá el token que te imprime, y en Postman: header Authorization, valor Bearer <token que copiaste>.

dotnet user-jwts usa la misma infraestructura que dotnet user-secrets (que ya usaste para la connection string) — guarda todo en tu perfil de usuario local, nunca en un archivo que se comitea.

6. ¿Y las cookies?

ASP.NET Core también soporta autenticación por cookie (más parecido a lo que quizás conocés de sesiones tradicionales) — tiene sentido para apps server-rendered donde el mismo servidor sirve el HTML. Para una Web API consumida por un cliente separado (tu React, Postman, una app mobile), Bearer token es la norma: no depende de que el cliente y el servidor compartan el mismo dominio, y evita la complejidad extra de protección CSRF que las cookies necesitan.
