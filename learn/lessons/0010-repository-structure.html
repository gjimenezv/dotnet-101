Models vs Repositories: quién hace qué, y cómo se organizan

Objetivo: saber identificar qué entidad necesita su propio repository, cómo estructurar las carpetas, y poder justificar cuándo está bien mezclar acceso directo con repository — la pregunta natural después de la lección 7.

En la lección 7 viste qué es el repository pattern. Acá va el paso siguiente, más práctico: cuando tenés 6 entidades en tu proyecto, ¿armás 6 repositories? ¿Dónde vive cada archivo? ¿Y está mal que algunas entidades usen repository y otras no?

1. La responsabilidad de cada carpeta

La distinción es simple una vez que la ves: Models describe qué es el dato. Repositories describe cómo se consigue/guarda.

ModelsRepositories
ContienePropiedades, navigation propertiesLINQ, .Include(), SaveChangesAsync()
¿Conoce EF Core / DbContext?NoSí
Cambia cuando...cambia la forma del dato (agregás una columna)cambia cómo lo consultás (una pregunta de negocio nueva)
Un Customer.cs es tu interface Customer { ... } de TypeScript — describe la forma, no sabe que existe una base de datos. Un CustomerRepository.cs es la función fetchCustomer() de tu API client — sabe cómo ir a buscarlo, pero no define qué es un cliente.

2. Cómo fluye una request, capa por capa

La regla que se ve en el diagrama: cada capa solo conoce a la de al lado. El Controller no sabe qué es un DbSet; el Repository no sabe qué es un HttpContext; el Model no sabe que existe ninguna de las dos. Si en algún momento estás por escribir LINQ dentro de un Controller, o devolver un Customer con propiedades HTTP pegadas, es señal de que se está mezclando una capa con otra.

Ojo con confundir Repository con Service (el IProductService que viste en la lección 3 era solo un ejemplo genérico de DI, antes de meter EF Core). No es lo mismo: un Repository solo sabe hacer queries/writes contra la base — es tu capa de acceso a datos, como un wrapper de Prisma. Un Service (el equivalente al de Express) orquesta lógica de negocio: puede llamar a varios repositories, validar reglas, decidir qué pasa si algo falla. Ejemplo: CustomerRepository.GetTopSpendersAsync() es una query, vive en el repository. "Crear una Order: chequear stock en Product, calcular el total, aplicar descuento si el Customer es VIP, recién ahí guardar" ya es una regla de negocio que coordina dos repositories — eso iría en un OrderService, no en ningún repository. Este proyecto no tiene una capa de Service explícita porque la lógica es mayormente queries; si tuvieras algo como el ejemplo de Order, ahí sí insertarías un Service entre el Controller y los Repositories.

3. ¿Un repository por modelo?

No — un repository por aggregate root, no por modelo. Un aggregate root es una entidad que tiene sentido pedir/guardar por sí sola. Todo lo que solo existe en el contexto de otra entidad se consulta a través del repository de esa otra entidad.

La pregunta que lo decide: "¿alguna vez voy a decir 'dame este X' sin pasar primero por otra entidad?" Si sí, tiene su propio repository. Si no, no.

Aplicado al schema de tu proyecto (Categories/Products/Customers/Orders/OrderItems/Employees):

Entidad¿Repository propio?Por qué
CustomerSíLo pedís directo: "dame los top spenders"
EmployeeSíSe consulta solo: "dame la cadena de jefes de este empleado"
ProductSíSe lista y filtra de forma independiente
OrderSíSe pide directo por su Id
OrderItemNoNunca tiene sentido fuera de una Order — se consigue vía orderRepository.GetByIdAsync(id) con .Include(o => o.Items)
CategoryDependeSi solo la usás vía Product.Category, no. Si vas a listar categorías sueltas, sí.
El error común es crear un repository por cada clase en Models/ sin pensar en esto — termina siendo puro boilerplate (un IOrderItemRepository con un solo método que nadie llama directo). Si en la entrevista te preguntan por qué OrderItem no tiene repository, esta es la respuesta.

4. Estructura de carpetas

ShopApi/
  Models/              (ya lo tenés — entidades, sin lógica de acceso a datos)
  Data/                (ya lo tenés — DbContext)
  Repositories/
    ICustomerRepository.cs
    CustomerRepository.cs
    IEmployeeRepository.cs
    EmployeeRepository.cs
    IProductRepository.cs
    ProductRepository.cs
  Controllers/
    CustomersController.cs

Un archivo por tipo — interfaz e implementación separadas, pero en la misma carpeta (no Repositories/Interfaces/ vs Repositories/Implementations/, eso es más ruido que ayuda). Carpeta plana; solo si el proyecto crece mucho tiene sentido anidar por agregado (Repositories/Customers/, Repositories/Orders/).

5. Crear y editar cada uno

Un modelo se edita cuando cambia la forma del dato — agregás una propiedad, agregás una navigation property. No debería tener ningún using Microsoft.EntityFrameworkCore ni lógica de consulta adentro.

public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;
    public string City { get; set; } = null!;
    public DateTime JoinedDate { get; set; }
    public ICollection<Order> Orders { get; set; } = new List<Order>();
}

Un repository se edita cuando necesitás una pregunta nueva contra la base de datos. El repository de Order es quien resuelve el acceso a OrderItem — fijate cómo OrderItem nunca aparece en su propia interfaz:

public interface IOrderRepository
{
    Task<Order?> GetByIdWithItemsAsync(int id);
}

public class OrderRepository : IOrderRepository
{
    private readonly ShopDbContext _context;
    public OrderRepository(ShopDbContext context) => _context = context;

    public Task<Order?> GetByIdWithItemsAsync(int id) =>
        _context.Orders
            .Include(o => o.Items)
            .ThenInclude(i => i.Product)
            .FirstOrDefaultAsync(o => o.Id == id);
}

6. ¿Está bien mezclar repository y DbContext directo en el mismo proyecto?

Sí — y es más común de lo que parece. No es una regla de todo-o-nada.

RepositoryDbContext/DbSet directo
Entidades con queries de negocio complejas y reusadas (Customer, Order)Lecturas simples de una sola tabla, sin lógica (Category para un dropdown)
Donde importa poder mockear en tests unitariosDonde el endpoint es prácticamente un CRUD de un objeto

Lo que sí importa en la entrevista no es "¿usaste repository en el 100% del proyecto?" — es que puedas explicar por qué una entidad lo tiene y otra no. Consistencia dogmática ("todo debe pasar por un repository") suele ser peor señal que una decisión justificada caso por caso.

Checkpoint del proyecto

Ejemplo de punta a punta — ICustomerRepository, con un método simple y uno con la lógica que ya viste en la lección 6 (top spenders):

public interface ICustomerRepository
{
    Task<Customer?> GetByIdAsync(int id);
    Task<List<Customer>> GetTopSpendersAsync(int minOrders);
}

public class CustomerRepository : ICustomerRepository
{
    private readonly TuDbContext _context;
    public CustomerRepository(TuDbContext context) => _context = context;

    public Task<Customer?> GetByIdAsync(int id) =>
        _context.Customers.FirstOrDefaultAsync(c => c.Id == id);

    public Task<List<Customer>> GetTopSpendersAsync(int minOrders) =>
        _context.Customers
            .Where(c => c.Orders.Count(o => o.Status == "Shipped") >= minOrders)
            .ToListAsync();
}

Registralo en Program.cs: builder.Services.AddScoped<ICustomerRepository, CustomerRepository>();

Ahora armá vos IEmployeeRepository y IProductRepository (y ICategoryRepository si decidiste que lo necesita), y decidí qué método necesita cada endpoint de la sección 3 de la definición del proyecto.

Si al aplicar la regla del "¿lo pido solo o no?" a tu propio schema te queda alguna entidad en duda (por ejemplo Category), preguntame y lo pensamos juntos con el caso real.
